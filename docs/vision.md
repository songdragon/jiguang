# 吉光项目愿景

**状态**　设计，待实现

## 产品定位

吉光（Jiguang）是一个独立的 coding agent。用户给出目标和约束，吉光在本地 Git 工作区内调查代码、实施修改、运行验证，并交付可检查的 diff、验证结果和剩余事项。用户可以指定模型，切换模型时仍能沿用同一套任务、工具和验证规则。

吉光也用于学习和验证 agent harness 的开发方法。任务推进、上下文构造、工具调用、执行恢复和完成判定由项目直接控制。每个机制都应能通过事件、日志和固定任务集观察其效果。

吉光与 Baize 各自独立。Baize 负责在现有厂商 agent 之间交接任务，以利用各家的已有额度。吉光直接通过用户配置的模型 API 执行任务，形成自己的模型调用、工作区操作和验证链路。两者各自维护仓库、任务状态和发布节奏。未来可以通过明确的外部接口集成，首阶段各自运行。

## 用户体验

1. 用户进入一个 Git 工作区，选择模型，描述要完成的修改。吉光记录验收条件，并保留运行前工作区状态。
2. 吉光定位修改点、应用补丁、执行适用的验证。用户能看到关键操作、进度、失败原因和消耗。
3. 发生网络断开、进程退出或预算耗尽时，吉光保存已知状态。用户恢复任务后，可以从已有 diff 和验证证据继续。
4. 有充分证据时交付结果。证据不足时报告当前状态、缺失条件和未解决的问题，用户可以决定是否继续。

## 首阶段范围

| 交付 | 首阶段范围 |
| --- | --- |
| 使用方式 | macOS 和 Linux 的本地 CLI，单个 Git 工作区内同一时间一条执行链 |
| 模型 | 原生 OpenAI Responses 适配器，加可脚本化的 Fake Provider；用户显式选模型 |
| 工具 | 文件读取、仓库搜索、应用补丁、写文件、运行命令 |
| 任务可靠性 | 持久化事件、查看状态、取消、显式恢复及不确定副作用的对账 |
| 质量控制 | 基于任务要求、工作区状态和验证记录的完成判定 |
| 评估 | 本地固定任务集、故障注入、可重复的结果记录 |

“本地”描述工具执行、工作区和任务存档的位置。选择远程模型时，上下文中选中的代码和工具结果会发给该模型服务。命令权限和进程隔离见 [技术架构](architecture.md)。

桌面或 Web 工作台、更多模型协议、MCP、Skills、后台摘要、模型自动路由、评审模型和多 agent 协作进入后续阶段。引入优先级由真实使用和评估数据决定。

## 衡量标准

| 指标 | 口径 |
| --- | --- |
| 实际完成率 | 外部验收通过的任务数 / 已发起的评估任务数 |
| 误报完成率 | 吉光判定完成但外部验收失败的任务数 / 吉光判定完成的任务数 |
| 中断恢复率 | 注入中断后恢复至外部验收通过且没有重复副作用的任务数 / 注入中断的任务数 |
| 人工返工 | 每个任务为达成验收所需的人工修补与追加指令，记录次数和原因 |
| 时间和消耗 | 记录耗时、工具调用次数、模型 token；价格缺失时记为未知 |

首轮先建立基线。对比 harness 变更时尽可能固定模型、任务、初始工作区、工具权限和预算，并记录适配器及配置版本。故障场景的判定及开发阶段见 [技术架构](architecture.md)。
